# @orchestra-design-system/themes

Theme entry points for the Orchestra design system.

This package is the public token layer for applications and Storybook. It owns token source files and generates the light and dark CSS bundles consumed by the core components and wrapper packages.

## Token model

Orchestra uses a three-tier token structure:

```text
Primitive → Semantic → Component
```

| Tier      | Source file(s)                                       | Purpose                                                           | Exported to CSS?    |
| --------- | ---------------------------------------------------- | ----------------------------------------------------------------- | ------------------- |
| Primitive | `tokens/primitive.json`                              | Raw values: colors, spacing, radius                               | No (reference only) |
| Semantic  | `tokens/semantic.light.json`, `semantic.dark.json`   | Meaningful values tied to a role or state, referencing primitives | Yes                 |
| Component | `tokens/component.light.json`, `component.dark.json` | Optional overrides for a specific component                       | Yes                 |

This keeps the token system hierarchical and avoids unnecessary duplication: components should reference semantic tokens, and only fall back to component-level tokens when the semantic layer isn't precise enough.

### Resolution trace

A single value flows through all three tiers before it reaches a component:

```jsonc
// 1. tokens/primitive.json — raw value
"color": { "purple": { "600": { "$value": "#7b55ad" } } }
```

```jsonc
// 2. tokens/semantic.light.json — meaningful reference to the primitive
"color": { "action": { "primary": { "container": {
  "default": { "$value": "{color.purple.600}" }
}}}}
```

```jsonc
// 3. tokens/component.light.json — optional component-specific token
"button": { "primary": { "container": {
  "radius": { "$value": "{radius.action.primary.container}" }
}}}
```

```css
/* 4. dist/css/light.css — generated by Style Dictionary */
:root {
  --orchestra-color-action-primary-container-default: #7b55ad;
  --orchestra-button-primary-container-radius: 0.5rem;
}
```

```css
/* 5. packages/core/src/components/button/button.css — consumed */
.button--primary {
  background-color: var(--orchestra-color-action-primary-container-default);
  border-radius: var(--orchestra-button-primary-container-radius);
}
```

## Usage

### 1. Import the theme CSS

Applications and Storybook import the generated bundles once, at the app root:

```css
@import '@orchestra-design-system/themes/light.css';
@import '@orchestra-design-system/themes/dark.css';
```

```ts
import '@orchestra-design-system/themes/light.css'
```

This defines all `--orchestra-*` custom properties on `:root` (light, the default) and scopes the dark overrides under `.orchestra-theme--dark`.

### 2. Switch themes

Toggle dark mode by adding the `orchestra-theme--dark` class to any ancestor element (or `<body>` for the whole app):

```html
<!-- Light (default) -->
<orchestra-button>Light Button</orchestra-button>

<!-- Dark -->
<div class="orchestra-theme--dark">
  <orchestra-button>Dark Button</orchestra-button>
</div>
```

### 3. Consume tokens inside components

Component styles reference generated custom properties directly — never hardcoded values. Provide a fallback value for resilience when the theme package hasn't loaded yet:

```css
/* packages/core/src/components/button/button.css */
.button--primary {
  background-color: var(--orchestra-color-action-primary-container-default);
  color: var(--orchestra-color-action-primary-content-default);
  border-radius: var(--orchestra-button-primary-container-radius);
}

/* packages/core/src/components/checkbox/checkbox.css */
.checkbox {
  border-radius: var(--orchestra-radius-action-primary-small, 0.25rem);
  border-width: var(--orchestra-size-action-primary-border-width-default, 2px);
}
```

### 4. Naming convention

The naming convention is a direct expression of the token architecture: each segment of a CSS variable name maps to a layer of the system that classifies _what_ a token is for, not just where it sits in a file.

**Semantic level**:

```text
--orchestra-{category}-{domain}-{variant}-{target}-{state}
```

| Segment    | Example value | Meaning                                                                |
| ---------- | ------------- | ---------------------------------------------------------------------- |
| `category` | `color`       | kind of value: `color`, `spacing`, `radius`, or `size`                 |
| `domain`   | `action`      | functional area the token belongs to                                   |
| `variant`  | `primary`     | visual weight/importance within the domain                             |
| `target`   | `container`   | part of the component the token styles                                 |
| `state`    | `default`     | interaction state; non-color tokens may end in a scale such as `large` |

Example: `--orchestra-color-action-primary-container-default` → category `color`, domain `action`, variant `primary`, target `container`, state `default`.

**Component level**:

```text
--orchestra-{component}-{variant}-{target}-{property}-{state}
```

| Segment     | Example value | Meaning                                                                                |
| ----------- | ------------- | -------------------------------------------------------------------------------------- |
| `component` | `button`      | the component name                                                                     |
| `variant`   | `primary`     | visual weight/importance within the component                                          |
| `target`    | `container`   | part of the component the token styles                                                 |
| `property`  | `radius`      | the CSS property, when the token isn't a color                                         |
| `state`     | —             | only present when the value varies by interaction state; omitted for static properties |

Example: `--orchestra-button-primary-container-radius` → component `button`, variant `primary`, target `container`, property `radius` (static, no state).

All segments are lowercase, kebab-case. Only semantic and component tokens are exported to CSS — primitives are referenced internally and filtered out during generation.

## Build

```bash
npm run build
```

This generates the distributed CSS bundles used by the design system and apps that consume it.

### Naming monitor

Each build also writes `dist/naming-monitor.html`. The page has one section per level: Primitive, Semantic and Component. Each level has its own naming columns, so primitive names (`color.grey.200`, `scale.x1`) are not checked against the semantic convention. Each token name is split into words, and each word is placed in the column whose allowed words or pattern include it. Words with no matching column are listed in the Issues column as Not applicable words, with advice on how to fix each one. Each section has its own advice table, which lists Not applicable words and same-layer tokens in one table with a Type column. The table is not rendered when a section has no issues.

- The Used by column lists the tokens that alias each token through a `{...}` reference, and the component folders in `packages/core/src/components` that reference it with `var(...)`, prefixed with `component:`. For primitives, this shows which semantic tokens use them.
- A token whose value aliases another token in the same level through a `{...}` reference is listed in the Issues column as a same-layer token, with the advice "Avoid cannibalism, a design token should always never consume a design token from the same layer." Rows with no issues leave that column empty.
- Primitives are not emitted to CSS, so they show a single raw value column.
- Category and Component match the first word of a token name only.
- Domain, Variant, Target, Property and State match any later word from their list.
- Primitive Step matches numbers, `x` scale steps, `none`, `full` and `transparent`.
- The allowed words are defined in `NAMING_COLUMNS` and `PRIMITIVE_COLUMNS` in `build.mjs`. Update those lists when the convention changes.

## Notes

- Token sources live in `tokens/`.
- CSS generation is handled by Style Dictionary.
- The core package consumes these variables, rather than owning the generated theme CSS itself.
- The public theme package is the recommended entry point for applications and Storybook.
